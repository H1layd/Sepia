# Sepia Split — протокол четвёртого режима (черновик v0.1)

Четвёртый режим транспорта профиля рядом с Tor, I2P и прокси. Не луковая
маршрутизация: каждый поток режется на доли по схеме Шамира и идёт
**параллельно** через несколько независимых узлов к общему **сборщику**.

Статус: утверждён владельцем как направление (18.11.2026). Это спецификация
для прототипа; криптография только стандартная, своих шифров нет.

## 1. Роли

| Роль | Что делает | Что знает |
|---|---|---|
| **Клиент** (браузер) | режет поток на доли, шлёт их через k узлов, собирает ответ | всё о себе |
| **Узел** (relay) | пересылает доли между клиентом и сборщиком | IP клиента, объём и время; содержимое и цель — нет |
| **Сборщик** (collector) | собирает доли в поток, открывает TCP к сайту, режет ответ на доли | цель (с HTTPS — только имя сайта); IP клиента — нет, только IP узлов |
| **Каталог** | публикует подписанный список узлов и сборщиков | ничего о трафике |

Правило пути: k узлов **в разных странах, у разных провайдеров (AS) и
разных операторов**; ни один узел не совпадает со сборщиком.

## 2. Разделение

- Схема Шамира над GF(2^8), параметры `t из k` (по умолчанию 2 из 3,
  в строгом режиме 3 из 5). Каждый байт ячейки делится независимо;
  одна доля — равномерный шум.
- Делится **ячейка** фиксированного размера `CELL = 1024` байт полезной
  нагрузки (с заголовком потока, см. §4). Последняя ячейка дополняется.
- Каждой ячейке — случайный 128-битный `cell_id` (один на все её доли) и
  номер доли `x ∈ 1..k`. Сборщику достаточно любых `t` долей с одним
  `cell_id`; лишние отбрасываются.

## 3. Каналы и шифрование

- **Клиент ↔ узел**: TLS 1.3 с отпечатком как у Chrome, внутри Noise
  `NK` (X25519, ChaCha20-Poly1305, BLAKE2s) с ключом узла из каталога.
  Снаружи — обычный HTTPS (HTTP/2 CONNECT или WebSocket на 443).
- **Узел ↔ сборщик**: Noise `NK` с ключом сборщика.
- **Клиент ↔ сборщик (сквозное)**: Noise `NK` поверх долей — сборщик
  видит открытый поток только после сборки, узлы не видят даже
  зашифрованного потока целиком.
- Ключи узлов меняются раз в сутки; каталог публикует новые заранее.

## 4. Потоки (не только «запрос–ответ»)

Нужно для WebSocket, потокового fetch, видео. Сквозной канал клиент↔сборщик
несёт мультиплексированные потоки:

```
ячейка (до разделения), 1024 байта:
  stream_id  u32   — поток внутри профиля
  seq        u32   — порядковый номер в потоке
  kind       u8    — OPEN / DATA / CLOSE / PADDING / WINDOW
  len        u16   — сколько байт полезных
  payload    [..]  — для OPEN: "host:port"; для DATA: байты
  padding          — до 1024
```

- `OPEN host:port` — сборщик открывает TCP к сайту (DNS — у сборщика,
  никогда у клиента). Только TCP: UDP/QUIC не поддерживаются, WebRTC — через
  TURN поверх TCP.
- `WINDOW` — управление окном (как в HTTP/2), чтобы быстрый сайт не
  переполнял медленный клиент.
- `PADDING` — пустые ячейки для постоянного потока (§5).

## 5. Защита от анализа времени

Сговор «один узел + сборщик» может связать клиента с сайтом по времени,
не собирая долей. Поэтому:

1. **Постоянный поток**: клиент к каждому узлу шлёт ячейки с постоянной
   частотой (например, 50 ячеек/с), пустые — как `PADDING`. Узлы делают то же
   к клиенту.
2. **Пачки у сборщика**: сборщик выпускает собранные ячейки наружу и
   отправляет доли ответов раз в `BATCH = 50–200 мс`, вперемешку между всеми
   клиентами.
3. Режимы профиля:
   - **быстрый** — без постоянного потока и пачек (защита: один узел,
     провайдер, сайт);
   - **приватный** — постоянный поток + пачки (защита и от сговора узел+сборщик).

## 6. Каталог и старт

- Несколько независимых серверов каталога; список действителен с подписями
  большинства (Ed25519). Клиент хранит их открытые ключи в сборке.
- Запись узла: адрес, порт, ключ Noise, страна, AS, оператор, роли, полоса.
- **Старт через DoH-канал**: если каталог заблокирован, клиент получает
  список и мосты TXT-запросами через публичные DoH-резолверы к нашему
  домену; ответы подписаны так же.
- **Мосты** — узлы, которых нет в публичном списке, раздаются по запросу.

## 7. Встраивание в браузер

- Режим профиля `split` в `net.rs`: тот же единственный сетевой вход, что для
  Tor / I2P / прокси. HTTP, WebSocket, потоковый fetch идут через `OPEN`/`DATA`.
- **Свой поток на каждый сайт** (вкладку верхнего уровня): разные `stream_id`
  и, если сборщиков несколько, разные сборщики — сайты не склеиваются по IP.
- Персона профиля: страна и часовой пояс — по стране сборщика; одна
  персона на всех пользователей режима.
- Killswitch профиля: нет t живых узлов — запросы не уходят никуда.
- `--audit` показывает режим, узлы, сборщик и параметры t/k.

## 8. От чего защищает (и от чего нет)

| Противник | Результат |
|---|---|
| Провайдер, Wi-Fi | видит HTTPS к узлам; не видит сайты и содержимое |
| Один узел (или < t узлов) | шум; не видит ни сайта, ни данных |
| Сборщик | видит сайт, не видит IP клиента |
| Сайт | видит IP сборщика, общую персону |
| Узел + сборщик в сговоре | быстрый режим: могут связать по времени; приватный: сильно затруднено |
| t узлов в сговоре | читают поток — поэтому узлы у независимых операторов |
| Глобальный наблюдатель | частично: постоянный поток и пачки мешают, но это не Tor |
| Владелец всех узлов | защиты нет (пока все узлы — наши) |

## 9. Прототип

Инфраструктура: 3 VPS-узла (разные страны и хостеры) + 1 VPS-сборщик
(хостер, терпящий выходной трафик) + домен для DoH-канала и маскировки.

Порядок:
1. Библиотека долей и формат ячейки + тесты (локально, без сети).
2. Сборщик и узел как один бинарник с ролями; клиент в `net.rs`; быстрый режим.
3. Постоянный поток и пачки; приватный режим; симулятор «узел + сборщик».
4. Каталог с подписями, DoH-старт, мосты.
5. Внешние операторы узлов, аудит — только после этого заявлять
   защиту сильнее «от обычной слежки».
